Hexagon CPU architecture support
================================

QEMU's TCG emulation includes support for v65, v66, v67, v68, v69, v71, v73,
v75, v77, v79, v81, v83, v85.
It also has support for the following architecture extensions:

- HVX (Hexagon Vector eXtensions)
- `HVX floating point <https://docs.qualcomm.com/doc/80-N2040-61/topic/hvx-floating-point.html>`_.
- HLX (see the `HLX reference manual
  <https://docs.qualcomm.com/doc/80-N3040-23/topic/hlx.html>`_).

User-DMA and HMX are not yet implemented.

Machine configurations also select the available HVX contexts, VTCM,
and HMX/HLX resources. See :doc:`machines` for the machine configurations.

For information on the specifics of the HVX extension, please refer
to the `Qualcomm Hexagon V79 HVX Programmer's Reference Manual
<https://docs.qualcomm.com/doc/80-N2040-61/>`_.

Emulation limits
----------------

The system models target functional execution.

HVX uses 128-byte vectors; 64-byte mode is not implemented.

See :doc:`../../devel/hexagon-sys` and
:doc:`../../devel/hexagon-l2vic` for system-register, TLB, and interrupt
details relevant to OS and firmware authors.

Performance Monitoring Unit (PMU)
----------------------------------

Every Hexagon system machine includes a PMU. Each vCPU is linked to a shared
``hexagon-pmu`` device holding the 8 configurable event counters (``PMUCNT0``-``PMUCNT7``)
and their event-select registers (``PMUEVTCFG``, ``PMUEVTCFG1``,
``PMUCFG``, ``PMUSTID0``, ``PMUSTID1``), plus the ``GPMUCNT0``-``GPMUCNT7``
global-monitor aliases (readable when ``SSR.PE`` is set).
The read-only ``UPMUCNT0``-``UPMUCNT7`` user-mode aliases, which are also
readable only when ``SSR.PE`` is set, are implemented too.
Guest software configures a counter's event through
``PMUEVTCFG``/``PMUEVTCFG1`` (event id bits 7:0) and ``PMUCFG`` (event id
bits 9:8, plus the thread mask), and reads it back through the matching
``PMUCNTn``. The whole unit is gated by ``SYSCFG.PM``: while it is clear no
counter advances and no extra code is generated by the packet translator, so
the PMU costs (almost) nothing until a guest actually turns it on.

Events implemented
^^^^^^^^^^^^^^^^^^^

QEMU's TCG emulation is a functional simulator: it has no cache, branch
predictor, bus, or pipeline timing model. Only PMU events derivable from
packet decode and commit are implemented:

================================== ========= ==========================================
Event                              Event id  Notes
================================== ========= ==========================================
``COMMITTED_PKT_ANY``              0x003     Packets committed, summed across all
                                              hardware threads
``COMMITTED_PKT_T0``-``T7``        0x00c-    Packets committed by one specific hardware
                                    0x016     thread
``COMMITTED_LD``                   0x030     Load instructions committed
``COMMITTED_ST``                   0x031     Store instructions committed
``COMMITTED_MEMOP``                0x032     ``memop``-attributed instructions committed
``HVX_PKT``                        0x111     HVX packets committed, summed across all
                                              hardware threads
``HVX_PKT_THREAD``                 0x112     HVX packets committed by the requesting
                                              hardware thread
``HVXPIPE_ALU``                    0x128     HVX ALU-class instructions committed
``HVXPIPE_MPY``                    0x129     HVX multiply-class instructions committed
``HVXPIPE_SHIFT``                  0x12a     HVX shift-class instructions committed
``HVXPIPE_PERM``                   0x12b     HVX permute-class instructions committed
``HLXFIFO_PKT``                    0x1a2     HLX packets committed, summed across all
                                             hardware threads
``HLXLD``                          0x1a6     HLX load traffic, in 128-byte beats (16
                                             per 2KB HLX vector load)
``HLXST``                          0x1aa     HLX store traffic, in 128-byte beats (16
                                             per 2KB HLX vector store)
``HLXSLOT_ALU``                    0x1af     HLX common-ALU instructions committed
``HLXSLOT_SHIFT``                  0x1b0     HLX shift-class instructions committed
                                             (including the paired ALU forms, which
                                             execute in the shift slot)
``HLXSLOT_MPY``                    0x1b1     HLX multiply instructions committed
``HLXSLOT_LD``                     0x1b2     HLX load instructions committed
``HLXSLOT_ST``                     0x1b3     HLX store instructions committed
================================== ========= ==========================================

Any other event id a guest selects is accepted -- the counter simply does
not advance -- and is logged once via ``LOG_UNIMP``, rather than silently
returning a fabricated count. This covers the majority of the architected
PMU event list: cache and TLB events, AXI/AHB bus transaction events,
branch-predictor events, and pipeline stall/replay/throttle events all
require a timing model this emulation does not have. The
``CYCLES_1_HVX_CONTEXTS_RUNNING`` through ``CYCLES_6_HVX_CONTEXTS_RUNNING``
events, and their HLX/coprocessor counterparts (``HLX_ACTIVE``,
``COPROC<n>_CYCLES_RUNNING``), are excluded for the same reason: an
accurate count needs a cycle-level model of concurrently-running
coprocessor contexts, which is not meaningful under QEMU's unsynchronized
multi-threaded TCG execution. The remaining HLX events (``HLXFIFO_*``
occupancy and stall events, ``HLXLD_*``/``HLXST_*`` buffer and conflict
events, ``HLXSLOT_EMPTY``, ``HLXREG_*``, ``VTCMEXEC_LLD``/``VTCMEXEC_LST``)
describe the coprocessor's hardware queues and are likewise unimplemented.

Modeling notes
^^^^^^^^^^^^^^

- All hardware threads on a core share one physical bank of 8 counters,
  the same way this emulation already models other cross-thread system
  registers such as ``MODECTL`` and ``SYSCFG``, rather than giving each
  hardware thread independent PMU state.
- Events with no ``_ANY``/``_THREAD`` or ``_T<n>`` variant
  (``COMMITTED_LD``, ``COMMITTED_ST``, ``COMMITTED_MEMOP``,
  ``HVXPIPE_ALU``/``MPY``/``SHIFT``/``PERM``) are summed across all
  hardware threads, like the shared counter bank they feed. A hypervisor
  may run a guest CPU on a different hardware thread each time it is
  scheduled, so a per-thread tally would not advance monotonically from
  the guest's point of view.
- Per-packet event counts are added to the vCPU's tallies once per
  translation block (and before any packet that accesses the PMU
  registers), not once per packet, to keep the cost of an enabled PMU
  low. If a translation block is left early because a memory access
  faults, the packets of that block that preceded the faulting one are
  not counted.
- The HLX events are tallied from the instructions in each committed
  packet, like ``COMMITTED_LD``: an HLX load or store with a false
  predicate is still counted. ``HLXLD``/``HLXST`` use the 128-byte unit
  the reference simulator's derived bandwidth statistics assume. The
  ``HLXSLOT_*`` buckets follow the execution slots of each HLX
  instruction (loads slot 1, stores slot 0, shifts slot 2, multiplies
  slot 3, common ALU slot 2 or 3). The ``hexagon-sim`` shipped with
  Hexagon SDK 6.7 does not report any of the HLX PMU events, so these
  counts could not be compared against it.
- HVX instructions that use two functional pipes in one op (for example
  a combined permute/shift or shift/multiply) are not attributed to any
  single ``HVXPIPE_*`` bucket: which physical pipe would execute them is
  not derivable from decode attributes alone.

For the full PMU event list and register layout, refer to the
`Hexagon V81 PMU Events reference
<https://docs.qualcomm.com/doc/80-N2040-60/topic/pmu-events.html>`_ and the
`Hexagon V81 HVX PMU Events reference
<https://docs.qualcomm.com/doc/80-N2040-61/topic/hvx-pmu-events.html>`_.
